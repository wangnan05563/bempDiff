# 详细设计：AI 分析增强 —— 项目级上下文理解模块

> 对应需求：差异化对比工具 · AI 分析增强（项目级上下文理解）
> 版本：v1.0 · 设计日期：2026-08-09
> 关联文档：详细设计-接口契约、需求规格说明书

---

## 1. 目标与需求映射

在现有「两阶段 AI 分析」（`stageA` 概览 + `stageB` 逐文件深读）基础上，新增**项目级上下文理解**能力：用户可选定一个工程/目录做完整代码分析，AI 据此获得架构、模块依赖、核心业务逻辑、配置与约定等全局认知，并将其作为分析依据，使结论更精准、更具针对性；分析结果须显式说明「项目级上下文如何影响当前结论」。

| 需求 | 设计落点 |
|------|----------|
| 1. 选择指定工程/目录做完整代码分析 | `ProjectContextAnalyzer` 扫描目录 → `ProjectContext`（纯 Java，无网络） |
| 2. 获取并理解项目级上下文（架构/依赖/业务/配置/约定） | `ProjectContext` 模型 + 扫描器自动抽取 `buildSystem/modules/dependencies/entryPoints/configFiles/conventions/summary` |
| 3. 将上下文融入分析过程 | `PromptBuilders` 注入「项目级上下文」章节；`stageA`/`stageB` 新增带上下文的接口重载 |
| 4. 结果包含上下文如何影响结论的说明 | `StageASummary`/`FileAnalysis` 增加 `contextInfluence` 字段；prompt 要求 LLM 产出该字段；`MarkdownReport` 渲染 |

## 2. 总体架构与数据流

```
┌──────────────┐   projectDir (可选)    ┌────────────────────────────┐
│ UI 目录选择  │ ─────────────────────► │ ProjectContextAnalyzer      │
│ / CLI --proj │                        │  .analyze(Path) → 纯扫描    │
└──────────────┘                        └─────────────┬──────────────┘
                                                      │ ProjectContext
                                                      ▼
  差异分析 (既有)  ── DiffResult + decompiled ──►  AiAnalyzer.stageA(diff, decompiled, cfg, ctx)
                                                      │  PromptBuilders.buildStageA(..., ctx)
                                                      │   → 注入「项目级上下文」章节
                                                      ▼
                                              StageASummary(+ contextInfluence)
                                                      │
                                                      ▼
                                   AiAnalyzer.stageB(cands, cfg, ctx)
                                                      │  PromptBuilders.buildStageB(..., ctx)
                                                      ▼
                                   List<FileAnalysis>(+ contextInfluence)
                                                      │
                                                      ▼
                                         MarkdownReport ── 渲染「上下文影响」段落
```

**关键原则：向后兼容。** 既有 3 参数 `stageA`/`stageB` 签名保持不变，新增 4 参数（`+ ProjectContext ctx`）重载为接口 `default` 方法，默认委托原实现。现有 `HttpAiAnalyzer`、`MockAiAnalyzer`、性能压测 `Harness`、既有测试**零改动**即可继续运行；仅「启用上下文增强」时走新路径。

## 4. 核心类设计

### 4.1 `ProjectContext`（模型）

```java
package com.bempdiff.ai.context;

public final class ProjectContext {
    private final String rootPath;
    private final String buildSystem;        // "Maven"/"Gradle"/"npm"/"none"
    private final List<String> modules;       // 模块名/相对路径
    private final List<String> dependencies;  // 人类可读的依赖描述
    private final List<String> entryPoints;   // 主类/入口文件
    private final List<String> configFiles;   // application.yml 等
    private final List<String> techStack;     // 技术栈关键词
    private final List<String> conventions;   // 包结构/命名约定
    private final String summary;             // 综合架构叙述（供 prompt）

    // 构造器 + getters
    public boolean isEmpty();                 // rootPath==null 视为未启用
    public String toPromptSection();          // 渲染为「## 项目级上下文」文本块
}
```

`toPromptSection()` 输出紧凑、可读、对 LLM 友好的文本，例如：

```
## 项目级上下文（分析依据）
- 构建系统：Maven（多模块）
- 模块：billing-core, billing-api, billing-web
- 核心依赖：spring-boot, mybatis, rocketmq, redis
- 入口/主类：com.x.BillingApplication, billing-web/IndexController
- 配置与约定：application.yml（多 profile）；包根 com.x.billing.*；DAO 层命名 *Mapper
- 架构简述：分层单体（core 领域 / api 接口层 / web 控制层），api 依赖 core，web 依赖 api
```

### 4.2 `ProjectContextAnalyzer`（扫描器）

```java
package com.bempdiff.ai.context;

public final class ProjectContextAnalyzer {
    public static final int MAX_FILES = 4000;   // 扫描上限，防超大目录（对齐 zip-bomb 防护哲学）
    public static final int MAX_DEPTH = 12;

    public ProjectContext analyze(Path root);
    // 内置：detectBuild(root) / extractDeps(root, buildSystem)
    //      findEntryPoints(root) / findConfigFiles(root) / inferTechStack(...)
    //      inferConventions(root)
}
```

抽取规则（启发式，纯文本/正则，无第三方依赖）：

- **构建系统识别**：存在 `pom.xml`→Maven；`build.gradle`/`build.gradle.kts`→Gradle；`package.json`→npm；`go.mod`→Go；`requirements.txt`/`pyproject.toml`→Python；否则 `none`。多模块 Maven/Gradle：解析 `<modules><module>` 或 `settings.gradle` 的 `include`。
- **依赖抽取**：
  - `pom.xml`：正则抓 `<artifactId>`（去重，截前 N=60 个）。
  - `build.gradle`：抓 `implementation`/`api`/`compileOnly` 后的 `'group:name:version'`。
  - `package.json`：抓 `dependencies`/`devDependencies` 的 key。
- **入口/主类**：文件名含 `Application`/`Main`/`Bootstrap` 且含 `public static void main`，或 `index.html`/`main.js`/`App.jsx`。
- **配置与约定**：`application.yml`/`application-*.yml`/`*.properties`/`*.conf`/`.env.example`；包根推断（`src/main/java` 下最深的公共前缀）；命名约定（`*Mapper`/`*Service`/`*Controller` 出现频次）。
- **架构叙述**：由「模块 + 依赖 + 入口 + 约定」合成一段 2–4 句自由文本 `summary`；若 `buildSystem==none` 或文件极少，则 `summary` 标注「未识别到标准构建系统，仅基于目录结构推断」。

> 不调用 LLM 生成叙述（保证离线、确定性、零成本）；LLM 在分析中结合该结构化上下文自行推理。

### 4.3 `PromptBuilders` 注入（重载）

```java
// 阶段A 重载：在 appendDiffHeader 后插入上下文章节
public static String buildStageA(DiffResult diff, Map<String,DecompiledUnit> decompiled,
                                 AiConfig cfg, ProjectContext ctx) {
    StringBuilder p = new StringBuilder();
    appendDiffHeader(p, diff, cfg);
    if (ctx != null && !ctx.isEmpty()) {
        p.append(ctx.toPromptSection()).append("\n");
        p.append("请在上述【项目级上下文】约束下评估：架构分层/模块依赖/配置约定如何影响本次差异的风险与影响；");
        p.append("输出 JSON 需额外包含字段 contextInfluence（字符串）：说明项目级上下文如何修正/支撑了你的结论。\n\n");
    }
    appendFileSummaries(p, diff, decompiled, cfg);
    return sanitize(p.toString(), cfg);
}

// 阶段B 重载：单文件深读时也附上下文（精简版：仅架构叙述 + 与该文件可能相关的模块/配置）
public static String buildStageB(String key, DecompiledUnit unit, FileClass fc,
                                 AiConfig cfg, ProjectContext ctx) {
    StringBuilder p = new StringBuilder();
    if (ctx != null && !ctx.isEmpty()) {
        p.append("## 项目级上下文（简要）\n").append(ctx.getSummary()).append("\n");
        p.append("请在分析本文件改动时，结合上述上下文判断其所属模块、上下游依赖与配置约定。\n\n");
    }
    // ... 原有 Java/前端分支措辞 + 要求输出 contextInfluence
}
```

### 4.4 模型扩展（需求 4）

`StageASummary` 增加：
```java
private String contextInfluence;          // 项目上下文如何影响整体结论
public String getContextInfluence(); public void setContextInfluence(String v);
```

`FileAnalysis` 增加字段与新构造器（**保留旧构造器**，避免破坏既有调用）：
```java
private String contextInfluence;
public FileAnalysis(String key, String intent, String risk, String impact,
                    List<String> testPoints, String contextInfluence) { ... }

```

### 4.5 解析扩展（需求 4）

`MockAiAnalyzer` 的 `parseStageAStatic`/`parseFileAnalysisStatic` 增加重载，捕获 `contextInfluence`：

```java
public static StageASummary parseStageAStatic(String resp) {
    return parseStageAStatic(resp, false);
}
public static StageASummary parseStageAStatic(String resp, boolean withContext) {
    StageASummary s = ...; // 原有逻辑
    if (withContext) s.setContextInfluence(pick(resp, "contextInfluence",
                                pick(resp, "上下文影响", "")));
    return s;
}
```

`pick()` 已支持 `field:` 纯文本与 `"field":` JSON 两种形态，新增字段零成本。LLM 未返回该字段时优雅降级为空串。

### 4.6 `AiAnalyzer` 接口（向后兼容）

```java
public interface AiAnalyzer {
    // 既有 3 参数签名保留
    StageASummary stageA(DiffResult diff, Map<String,DecompiledUnit> decompiled, AiConfig cfg);
    List<FileAnalysis> stageB(List<DecompileReq> candidates, AiConfig cfg);

    // 新增 4 参数 default：默认委托原实现（未启用上下文时行为不变）
    default StageASummary stageA(DiffResult diff, Map<String,DecompiledUnit> decompiled,
                                 AiConfig cfg, ProjectContext ctx) {
        return stageA(diff, decompiled, cfg);
    }
    default List<FileAnalysis> stageB(List<DecompileReq> candidates, AiConfig cfg,
                                      ProjectContext ctx) {
        return stageB(candidates, cfg);
    }
    // buildStageA/BPrompt、estimateTokens、testConnection 不变
}
```

`HttpAiAnalyzer`/`MockAiAnalyzer` **重写** 4 参数版本，调用带 ctx 的 `PromptBuilders` 重载与带 `withContext` 的解析；现有 3 参数版本委托保持原逻辑。

### 4.7 报告渲染（需求 4）

`MarkdownReport` 在：
- 阶段A 概览段：若 `summary.getContextInfluence()` 非空，追加 `**项目上下文影响**：<text>`；并新增一节「项目级上下文摘要」列出 `buildSystem/modules/dependencies/configFiles`（来自传入的 `ProjectContext`）。
- 逐文件段：若 `fa.getContextInfluence()` 非空，追加 `> 上下文影响：<text>`。

## 7. 风险、成本与权衡

- **Token 成本**：上下文章节增加 prompt 体积，已计入 `estimateTokens` 成本闸门（`Main` 既有逻辑），超阈值仍二次确认。扫描结果已压缩（`toPromptSection` 紧凑、依赖截前 60）。
- **LLM 输出可靠性**：`contextInfluence` 由 prompt 指令产出、轻量解析捕获，缺失即降级为空（不影响主结论）。量产后可换严格 JSON 校验。
- **扫描性能/安全**：`MAX_FILES`/`MAX_DEPTH` 上限防超大目录；仅读文本元数据，不触网、不执行代码。
- **向后兼容**：接口 default 方法 + 旧构造器保留，零破坏性变更；`MockAiAnalyzer` 离线回放无需 response 文件即返回空 `contextInfluence`。

5. **M5 集成**：CLI `--project` + UI 选择/开关 + `UiConfig` 持久化。
6. **M6 全量验证**：`build_and_test.sh` 全绿 + `package.ps1` 重新打包 + 端到端冒烟（`--project` 路径下跑 `ai`）。

## 9. 验收标准（AC）

- AC1：选定工程目录后，`ProjectContextAnalyzer` 能识别构建系统、模块、依赖、入口、配置文件与约定。
- AC2：启用时 `stageA`/`stageB` prompt 含「项目级上下文」章节；未启用时行为与旧版完全一致（无回归）。
- AC3：`StageASummary` 与 `FileAnalysis` 携带 `contextInfluence`，且报告可见「上下文影响」说明。
- AC4：既有 54 测试无回归；新增 3 测试通过；打包 exe 端到端可用。
- AC5：上下文章节纳入成本闸门估算，不引发意外超阈值静默失败。
