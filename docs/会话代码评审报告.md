> 评审范围：本会话内新增/修改的代码，覆盖 8 个关注维度。每条给出「位置 / 问题性质 / 影响 / 修复方向（不贴代码）」。
> 涉及文件：`Job.java`、`BempServer.java`、`JobStore.java`、`store.js`、`api/client.js`、`CompareOverlay.vue`、`DiffView.vue`、`diff_inline.js`、`severity.js`、`ReportPreview.vue`、`ConfigDialog.vue`、`main.css`、`dev-shell/main.js`。

## 1. 逻辑错误

**F1 · `BempServer.runCompareTask`（解析阶段）**
- 位置：解析分支（folder/package 两路）在「旧包解析 → 新包解析 → 标记 40%」之后才检查 `cancelRequested`（line 251）。取消请求在第二次解析（新包）期间不会生效。
- 性质：取消响应存在「盲区」——解析阶段整体只在尾部检查一次。
- 影响：大包比对时，点「取消比对」后仍要等新旧两个包都解析完才返回 CANCELLED，用户感知卡顿。
- 修复方向：在两次解析之间也插入一次取消检查；或把解析循环按文件分片，在分片边界检查。

**F2 · `store.cancelCompare`（取消失败静默）**
- 位置：`cancelCompare()` 先置 `activeCompareId=null` 让轮询退出，再 `api.cancelJob(id).catch(()=>{})` 发取消请求（fire-and-forget）。
- 性质：取消请求若因网络/后端异常失败，前端已停止轮询并表现为「已取消」，但后端任务仍在跑。
- 影响：UI 与后端状态不一致（界面说取消，后端继续占用资源），且用户无法感知失败。
- 修复方向：取消请求失败时应回退 `activeCompareId` 或给出错误提示，而不是静默吞掉。

**F3 · `ConfigDialog.onProviderChange`（厂商默认值识别错误）**
- 位置：切换厂商时仅用模块级 `prevBaseUrl` 与当前 `aiBaseUrl` 比较来判断「是否还是上一预设默认值」。
- 性质：默认值检测只看「上一个预设」，未与「所有预设默认值」比对。若当前 baseUrl 正是某预设默认值但 `prevBaseUrl` 已变，切换走时不会自动回填新预设的 baseUrl/model。
- 影响：用户从「仍是默认值」的 OpenAI 切到 DeepSeek 时，baseUrl 停留在 OpenAI 地址而 provider=deepseek，配置自相矛盾。
- 修复方向：检测 baseUrl 是否等于「任一预设的默认值」（或维护字段 dirty 标记），再决定是否自动填充。

**F4 · `dev-shell/main.js` `computeSize` / `createWindow`（最大化未真正生效）**
- 位置：`computeSize()` 在窗口放不下时返回 `{maximize:true}`，但 `createWindow` 在该分支只是用 `MIN_W/MIN_H` 创建窗口并 `win.show()`，**没有调用 `win.maximize()`**。
- 性质：逻辑与注释/意图不符（注释写「直接最大化」但代码未最大化）。
- 影响：在小于 960×640 工作区的屏幕上，窗口以最小尺寸创建且溢出屏幕、不可见最大化效果。
- 修复方向：在 `maximize` 分支真正调用窗口最大化（或在 `ready-to-show` 中按工作区全屏设置 bounds）。

## 2. 边界条件处理缺失

**B1 · `DiffView.rows` 解析器（正文行被误删）**
- 位置：以 `raw.startsWith('--- ')` / `'+++ '` 跳过 unified-diff 头，但未区分「头」与「源码正文中恰好以 `--- ` / `+++ ` 开头的行」（如源码注释里的 Markdown 分隔线）。
- 性质：协议行与正文行的前缀碰撞未隔离。
- 影响：极个别源码行被整行丢弃，差异展示缺行。
- 修复方向：仅在「恰好为 diff 头（`--- a/...`、`+++ b/...`）」时跳过；或基于 `@@` 之后的上下文更严谨地解析。

**B2 · `Job.cancelRequested` 检查窗口（构建阶段不可取消）**
- 位置：`runCompareTask` 的取消检查只在「解析后」「差异计算+统计后」两处；进入 `building`/`complete` 后不再检查。
- 性质：取消为「阶段边界」语义，但构建/回填阶段无边界检查。
- 影响：差异计算完成后的构建阶段无法被取消（通常很快，影响小，但语义不闭环）。
- 修复方向：在 `complete()` 前补一次取消检查，或文档明确「取消为尽力而为、以阶段为粒度」。

**B3 · `dev-shell/main.js` `ensureClasspath`（Windows argv 长度）**
- 位置：临时从源码编译时把所有 `.java` 绝对路径一次性塞进 `javac` 参数。
- 性质：未考虑 Windows 命令行长度上限（约 8k~32k）。
- 影响：java_core 源码较多时 `spawnSync(javac, ...)` 可能因 argv 过长静默失败，导致首次无产物时开发态兜底编译失败。
- 修复方向：改用 `@argfile`（`javac @args.txt`）或分批编译。

**B4 · `diff_inline.inlineDiff`（单侧为空时的退化）**
- 位置：`oldS` 或 `newS` 为空时 `lcsTokens` 返回 `[]`，导致调用方拿到「无片段」而非「整行 add/del」。
- 性质：空串边界未特判。
- 影响：当前只在「del/add 配对」时调用（双侧非空），故未触发；但该导出函数在其它场景被独立调用时会出现整行不显示高亮。
- 修复方向：单侧为空时直接返回「整段 add/del」片段，而非空数组。

## 3. 空值 / 异常处理不当

**N1 · `BempServer.handleEntry`（未校验任务是否完成）**
- 位置：`handleEntry` 直接 `job.oldSnap.getEntries().get(key)`，但**未检查 `job.status==DONE`**。
- 性质：缺少前置状态守卫，RUNNING/QUEUED 时 `oldSnap` 为 null。
- 影响：若比对尚未完成即请求反编译，抛 NPE → 500「反编译失败: null」；前端虽不会主动这样调，但属于不健壮的后端契约。
- 修复方向：任务未完成时返回 409/425 语义错误（如「比对尚未完成」）而非 NPE。

**N2 · `BempServer.handleReport` / `handleExport`（同 N1）**
- 位置：报告/导出均直接读 `job.oldSnap/newSnap/result`，无 DONE 守卫。
- 性质：同上，依赖前端「只在 DONE 后调用」的约定，后端未自守。
- 影响：比对未完成被调用时 NPE → 500。
- 修复方向：在 action 入口统一校验 `status==DONE`，否则返回明确错误。

**N3 · `store.selectEntry`（反编译结果缺 null 保护）**
- 位置：`if (!dec.ok)` 直接访问 `dec.ok`，未先判 `dec` 是否存在。
- 性质：`api.decompile` 异常时走 catch，正常时 `dec` 应为对象；但未对「响应体结构异常」做保护。
- 影响：极端情况下响应非预期结构会导致二次异常（被外层 catch 兜住，但不优雅）。
- 修复方向：访问 `dec.ok` 前先判 `dec && dec.ok` 或用可选链。

## 4. 变量作用域 / 生命周期

**S1 · `ConfigDialog` 模块级 `prevBaseUrl` 生命周期过长**
- 位置：`let prevBaseUrl = ''` 定义在 `<script setup>` 模块作用域，跨多次「打开/关闭」对话框持续存在。
- 性质：本应「每次打开对话框重置」的临时状态被提升为全局可变状态。
- 影响：关闭再重新打开对话框后，`prevBaseUrl` 保留上次值，导致「首次切换检测」语义跨打开周期串味（叠加 F3 的默认值误判）。
- 修复方向：在 `watch(()=>props.visible)` 打开时把 `prevBaseUrl` 重置为当前 `form.aiBaseUrl`（或重置为 ''）。

**S2 · `DiffView` `flashTimer` 未随卸载清理**
- 位置：`flashTimer` 在 `locate()` 中 `setTimeout` 设置，组件 `onUnmounted` 未清理。
- 性质：定时器引用已卸载实例的 `ref`。
- 影响：组件在 900ms 动画窗口内卸载时，定时器仍会写入 `flashRi`（Vue 允许写已卸载实例的 ref，无崩溃，但属生命周期疏漏）。
- 修复方向：在 `onUnmounted` 中 `clearTimeout(flashTimer)`。

## 5. 并发 / 状态一致性隐患

**C1 · 并发比对「前端放弃但后端仍跑」（资源）**
- 位置：用户在前一个比对轮询中途再点「开始比对」，`runCompare` 改写 `activeCompareId` 使旧轮询退出，但后端 `workers` 里旧任务已提交、会一直跑到完成。
- 性质：`activeCompareId` 仅协调前端轮询，后端无「前端已放弃」信号。
- 影响：被放弃的比对仍占用虚拟线程/磁盘 IO/内存，结果无人消费。
- 修复方向：前端放弃时可主动调一次 `cancelJob`；或后端对长时间无状态轮询的任务做空闲回收。

**C2 · `workers` 执行器无并发上限**
- 位置：`Executors.newVirtualThreadPerTaskExecutor()` 无界；每个比对提交一个任务。
- 性质：缺少背压/并发上限。
- 影响：用户连续狂点比对时，多个大包解析并发，可能耗尽文件句柄/内存/磁盘带宽。
- 修复方向：在 `workers` 外层加信号量/有界调度，限制同时进行的比对数。

**C3 · `Job` 字段写序与可见性（已正确，记录确认）**
- 位置：`complete()` 先写 `oldSnap/result/stats` 再写 `status="DONE"`（volatile 末位）。
- 性质：利用 volatile 写建立 happens-before，HTTP 读线程读到 `DONE` 时必可见全部回填字段。
- 影响：无缺陷——记录为「正确实现」，无需修改。
- 修复方向：保持现状即可。

## 6. 重复 / 冗余逻辑

**R1 · `DiffView.vue` 重复定义 `STATUS_CLS`**
- 位置：`DiffView` 内 `STATUS_CLS`（line 8-13）与 `store.js` 的 `STATUS_META` 完全重复同一映射；且 `DiffView` 已 `import { STATUS_META }` 却只用它取 `dot`，badge 仍用本地 `STATUS_CLS`。
- 性质：同一常量两处定义，违反单一数据源。
- 影响：日后改状态配色需改两处，易遗漏产生不一致。
- 修复方向：直接复用 `store.STATUS_META[node.status].cls`，删除本地 `STATUS_CLS`。

**R2 · `JobStore.seq` 死代码**
- 位置：`JobStore` 内 `AtomicLong seq` 从未被使用（jobId 由 `BempServer` 自己的 `seq` 生成）。
- 性质：冗余字段。
- 影响：无功能影响，但增加阅读干扰。
- 修复方向：删除未使用字段，或改由 JobStore 统一发号。

**R3 · 报告/导出重复反编译（`BempServer.handleReport`/`handleExport`）**
- 位置：`handleReport` 与 `handleExport` 各自重新 `buildClassMap`+`buildTextMap`+`LibJarDiff.analyze`，且每次请求都重算。
- 性质：昂贵的反编译/分析未被缓存到 `Job` 上，跨请求重复。
- 影响：大包「生成报告」+「导出」连续操作会做两遍重活，耗时翻倍。
- 修复方向：首次计算后把反编译结果缓存进 `Job`（或在同一次请求内复用同一 map）。

**R4 · `BempServer` 创建两个虚拟线程执行器**
- 位置：`server.setExecutor(newVirtualThreadPerTaskExecutor())` 与字段 `workers` 各一个。
- 性质：HTTP 请求与比对任务分属两个无界执行器，分开创建。
- 影响：无正确性错误，但多了一次执行器实例；监控/上限也需各管各。
- 修复方向：可复用同一个执行器实例（HTTP 与任务共用或显式区分但统一治理）。

## 7. 与原有代码风格的冲突

**G1 · `DiffView` 不用已导入的 `STATUS_META`（同 R1）**
- 位置：已 import `STATUS_META`/`STATUS_LABEL` 却另起 `STATUS_CLS`，风格上与「store 集中维护状态常量、组件共享」的既有约定冲突。
- 性质：局部重复 + 与既有约定相悖。
- 修复方向：统一走 `store.STATUS_META`，消除本地副本。

**G2 · `DiffView` 自定义类命名 `.row` 与 Bootstrap `.row` 撞名**
- 位置：scoped 样式里把 diff 行容器命名为 `.row`（Bootstrap 的 `.row` 是 flex 栅格）。
- 性质：命名撞车，易让维护者误读为栅格系统。
- 影响：scoped 下不冲突功能，但可读性差、易误导。
- 修复方向：改为 `.dv-row` 之类专属前缀。

**G3 · `ToolBar.buildOptions` 与 store 默认 `topK` 不一致**
- 位置：`buildOptions` 用 `c.topK ?? 12`，而 `defaultConfig()` 与 `ConfigDialog` 默认 `15`。
- 性质：同一语义的默认值在多处硬编码、数值不一致。
- 影响：配置未加载时（config 为 null）走 12，加载后走 15，行为轻微漂移。
- 修复方向：统一从 `state.config`/常量取，避免散落字面量。

## 8. 潜在性能缺陷

**P1 · `DiffView.inlineMap` 用 `rs.indexOf(d)` 反查行号（最值得修）**
- 位置：`inlineMap` 在配对 del/add 时，用 `rs.indexOf(d)` / `rs.indexOf(a)` 把行对象映射回 `res` 下标。
- 性质：每对用一次 `indexOf` → O(n) 查找；整体在最坏情况下趋近 O(n²)（n 为变更行数）。
- 影响：超大 diff（数千变更行）切换「词/字符级」高亮或折叠时会明显卡顿。
- 修复方向：配对循环本身已持有下标 `i/j/k`，直接用这些下标写 `res`，不要回查 `indexOf`。

**P2 · 报告/导出重复反编译（同 R3）**
- 位置：见 R3。
- 性质：重复 CPU/IO 密集计算。
- 影响：大包报告/导出延迟高。
- 修复方向：缓存到 Job 或请求内复用。

**P3 · 自动 AI 报告在比对主链路额外叠加负载**
- 位置：`runCompare` 完成后若 `autoAiOnCompare && aiEnabled` 会静默再跑一次 `generateReport(true)`。
- 性质：比对成功后立即触发一次完整 AI 反编译+分析（再次重算 decompiled map）。
- 影响：比对「完成」感出现后，后端仍在跑重活，可能拖慢后续交互；且重复反编译放大 P2。
- 修复方向：复用比对阶段已算产物，避免二次反编译。

**P4 · `colorizeReport` 每次 `reportMd` 变化全量 DOM 解析**
- 位置：`ReportPreview.html` 为 computed，依赖 `state.reportMd`，内部走 `DOMParser`+遍历所有 `strong`+向上爬祖先。
- 性质：报告越大，重算成本越高；但仅在报告变化时触发，尚可接受。
- 影响：超大报告重新着色略慢；当前非瓶颈。
- 修复方向：报告较大时可考虑分块/节流，或仅在需要时着色（非必须）。
