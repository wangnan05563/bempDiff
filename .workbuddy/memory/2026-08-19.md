## 优化 ZIP 包对比：嵌套 ZIP 自动解包 + 递归对比（修复核心缺陷）
- **根因（实测复现）**：`ArchiveTree.resolveTopArchive` 把「包对比模式」顶层条目的 `outerEntry`（外层包内条目名，如 `lib/bundle.zip`）**当磁盘路径** `Paths.get(outer)` 返回 → `ZipFile` 打开失败 `NoSuchFileException: lib\bundle.zip` → 嵌套归档无法解包、children 500。文件夹模式（outerEntry=真实磁盘路径）正常，故此前测试未暴露。
- **修复**（`bempdiff/java_core/src/com/bempdiff/diff/ArchiveTree.java`）：`resolveTopArchive` 仅当 `Files.isRegularFile(candidate)` 才直接打开；否则走 `PackageParser.readEntryBytes(snap, e)` 从 `snap.getFile()` 抽取条目落临时文件。目录结构纳入比对：`listArchive` 不再跳过目录条目；`deriveDirs` 由文件路径前缀 + zip 目录条目派生目录集合，`computeChildren` 输出 `isDir` 结构标记节点（expandable=false，状态 ADDED/DELETED/UNCHANGED，空目录/移动目录可见）。`statusRank` 加 dirs 参数。
- **新增自动递归解包**：`ArchiveTree.recursiveUnpack(oldSnap,newSnap,key)` 一次返回完整嵌套差异树（嵌套归档节点带 children），护栏 `MAX_RECURSION_DEPTH=12` / `MAX_RECURSIVE_NODES=20_000`；新端点 `GET /api/entry/recursive?jobId=&key=`（`BempServer.handleEntryRecursive`）。

- **测试**：新增 `NestedZipDiffTest`（7 用例：3 层嵌套 folder/package 模式、recursiveUnpack 全树、深度护栏、目录结构差异、深层内容 diff、单侧缺失），注册进 `build_and_test.sh`。全量 **121/121 绿**；`recursive_unpack_smoke.py` 扩到 10 步（3 层嵌套、recursive 端点、包模式嵌套）**全过**；`vite build` 36 模块过。

## AI 成本预估 67M tokens 排查与修复（计算无误但有界性缺陷）
- **排查结论**：预估与真实调用共用 `PromptBuilders.buildStageB`（指令 + ```diff + unit.getDiffText() ```），`estimateTokens=字符数/2`。classify 预估=Σ(topK=stageBTopK 默认15) 单文件 prompt 字符/2。用户场景 67,058,895 tokens ≈ 1.34 亿字符 = 15 文件×约 900 万字符/文件——**计算是忠实的**（真实 classify 也发同样内容），罪魁是**单文件 diff 无上限**：`LineDiff.unified` 输出整文件两侧（无 hunk 截断），整文件重写/超大文件（压缩 JS 美化后）时 diffText≈2×文件大小。且 chars/2 对代码是低估（真实 token 更多）。阈值显示 50 是用户自己配置（默认 8000）。

## 智能识别：同名不同版本压缩包自动按版本排序比对
- **需求**：`BEMP5.0-adapterV202301-02-036M061(20260707-1135).zip` vs `...036M059(20260703-1104).zip`——名称一致版本号不一致，应智能识别后自动比对（旧→新），不依赖用户手动分辨新旧。
- **新增 `com.bempdiff.parse.PackageVersion`**（纯静态工具）：
  - `extractFromFileName`：点分式（1.6.1/v2.0.1-SNAPSHOT）优先，其次构建号/时间戳式尾段 `036M061(20260707-1135)`（数字+字母+括号，取最右端匹配）。
  - `sameBaseDifferentVersion(a,b)`：两两比较——去扩展名后公共前缀 ≥4 字符、剩余尾段均形似版本（含数字且仅含 数字/字母/()/._-）且不同 → 同包不同版本（比正则稳，不依赖版本语法）。
